POSITION:
For a CI verification product gating agent stack changes in production, false negatives (rejecting valid alternative code) break developer trust, while false positives (accepting broken code) ruin safety. BenchMe must enforce execution-based correctness while strictly decoupling verification from implementation details. We resolve the strict-versus-weak tension by enforcing black-box behavioral contracts validated against alternate implementations, treating mutation survival as an informational metric rather than a gating filter, and keeping LLM judges completely out of the pass/fail correctness pipeline.

Q1: What is the minimum oracle a capsule must have to enter a decision-grade run?
A decision-grade capsule requires five mandatory components:
1. **Base Negative (Control 1):** Target verifier fails on unpatched base commit.
2. **Reference Positive (Control 2):** Reference patch passes target verifier and full regression suite.
3. **Full Regression Suite (Control 3):** Full suite execution verifies no collateral breakage.
4. **Anti-Tautology Check (Control 4):** No-op, empty, and superficial/hardcoded return patches fail.
5. **Alternate-Solution Control (Control 5):** At least ONE distinct, functionally valid alternate patch (generated via a non-reference model family or human) passes the verifier.
*Nice-to-have:* Control 6 (adversarial verifier harness probe) and AST-mutation coverage reports.

Q2: How is the strict-versus-weak tension resolved in practice?
By shifting verifiers from implementation-coupled unit tests to **black-box behavioral contracts**:
1. **Spec-Driven Assertions:** Verifiers may only assert on public API return values, state transformations, exported side-effects, and raised exception types. Assertions on private helper names, internal execution paths, or exact exception error message strings are strictly forbidden.
2. **Multi-Model Alternate Gate:** Every capsule must be executed against at least two independent implementations (the human reference patch plus at least one patch generated by an out-of-family frontier model).
3. **Disagreement Triage Procedure:** When an alternate patch fails the verifier:
   - If the alternate satisfies the task specification: **The verifier is flawed (over-specified).** Patch the verifier to evaluate behavior, not code structure.
   - If the alternate violates the task specification: **The alternate is invalid.** Fix the alternate patch.

Q3: Should mutation survival be a gate, a reported number, or dropped?
**Reported number only.** Mutation survival must NOT be a gate. Forcing high mutation kill rates incentivizes verifier authors to write low-level, implementation-specific assertions—the direct driver of the 59.4% test-flaw rate and 46.8% false rejection of valid alternatives. Given 2026 replicability evidence showing mutation scores are unreliable for defect-exposing quality outside standard regression, mutation survival should be reported strictly as informational diagnostic metadata.

Q4: Does an LLM judge have any role in the oracle, and if so exactly where?
**Narrow and strictly non-gating.**
- **Correctness Gate:** 0% LLM judge. Execution pass/fail is 100% deterministic code execution.
- **Allowed Roles:**
  1. *Capsule Synthesis:* Generating candidate alternate solutions during oracle creation (which are then verified deterministically by execution).
  2. *Post-Execution Audit:* Asynchronous, out-of-band flagging of reward-hacking patterns, scope creep, or maintainability anti-patterns for telemetry or human review routing. An LLM judge opinion must never flip an execution pass to a fail.

Q5: Does the model-tier axis change any of the above?
**Yes, fundamentally.** Open-weight and mid-tier models display higher structural variance in coding style, control flow, and standard library usage compared to frontier models. If an oracle is implementation-sensitive, cheap models will be penalized for valid but non-canonical code, artificially inflating their failure rate and corrupting the **cost per solved task** metric. Evaluating model tiers accurately requires an oracle that measures *functional correctness*, not adherence to a specific coding style.

STRONGEST OBJECTION TO MY OWN POSITION:
By prioritizing implementation-agnostic black-box verifiers and rejecting hard mutation gates, BenchMe risks under-specifying edge cases, allowing subtly incomplete patches (the 77% mutation survival failure mode) to pass CI unnoticed in customer codebases.

WHAT WOULD CHANGE MY MIND:
Empirical data from the pydantic corpus showing that requiring an alternate-solution control (Control 5) fails to catch implementation-locking flaws in >15% of cases, or evidence that mutation-hardened verifiers can achieve <5% false-rejection rates on out-of-distribution model patches.

CONFIDENCE: high — In a commercial CI verification product, false rejections destroy developer velocity and cause teams to disable the tool, making black-box behavioral verification the only viable foundation for agent CI.
