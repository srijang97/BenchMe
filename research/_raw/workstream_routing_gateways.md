## 3. The Nine Questions, Answered with Evidence

### Q1. What do generic routers actually solve today â€” prompt-level classification or workflow/trajectory routing?

**Fact:** Essentially all commercial routing is per-request classification. Not Diamond's router "analyzes each input and predicts which model will provide the highest quality response" ([docs](https://docs.notdiamond.ai/docs/what-is-model-routing)); RouteLLM routes single queries between a strong and weak model on preference data; OpenRouter's auto-router does per-prompt selection, and its only trajectory-awareness is **session stickiness** â€” pinning the *same* model/provider across a conversation to preserve prompt caches, i.e., deliberately *not* re-routing mid-trajectory ([auto-router docs](https://openrouter.ai/docs/guides/routing/routers/auto-router)) **[HARD]**. The academic literature explicitly diagnoses this: TwinRouterBench (May 2026) notes existing benchmarks "evaluate routers only on one-shot promptsâ€¦ never expose the router-visible prefix at an intermediate agent step, never test whether a cheaper replacement preserves downstream task success" ([arXiv 2605.18859](https://arxiv.org/html/2605.18859)) **[HARD]**. Agent-as-a-Router (June 2026) calls the failure mode "information deficit" of static one-off classification ([arXiv 2606.22902](https://arxiv.org/html/2606.22902)) **[HARD]**. **Verdict: prompt-level classification, plus non-learned reliability plumbing (fallbacks, load balancing) which is where most real gateway value currently sits.**

### Q2. Are routers expanding into coding-agent-specific routing?

**Yes, visibly, starting late 2025 / 2026.** Three hard data points: (1) **Not Diamond's "Pre-trained router: Code"** in early access, positioned precisely at "long-horizon coding agent cost," claiming 30%+ cost cuts ([docs](https://docs.notdiamond.ai/docs/pre-trained-router-code)) **[HARD product / MED claim]**; (2) **Vercel AI Gateway's dedicated coding-agents section** (Claude Code, Codex, OpenCode, Cline, Blackbox, Grok Build) ([vercel.com/ai-gateway](https://vercel.com/ai-gateway)) **[HARD]**; (3) **OpenRouter's app-rankings taxonomy** now has a formal coding category with subcategories (`cli-agent`, `ide-extension`, `cloud-agent`, `native-app-builder`) and a public Data API filterable by them ([app attribution docs](https://openrouter.ai/docs/app-attribution), [Data API](https://openrouter.ai/docs/cookbook/administration/data-api)) **[HARD]**. Kong and TrueFoundry both publish Claude Code governance guides **[HARD]**. **But note the asymmetry: gateways are capturing coding-agent *traffic* (governance, spend, keys); only Not Diamond and academia are attempting coding-specific routing *intelligence*.**

### Q3. Can routers learn from live traces without upfront benchmarks? What labels do they need?

**Fact:** Commercial custom routers today require labeled eval data upfront. Not Diamond needs (input, response, evaluation score) triples per candidate model â€” min 15 samples, practically thousands ([training docs](https://docs.notdiamond.ai/docs/router-training-quickstart)) **[HARD]**. RouteLLM needs pairwise preference labels (Chatbot Arena votes, optionally GPT-4-judge-augmented) ([paper](https://arxiv.org/html/2406.18665)) **[HARD]**. No commercial router advertises online learning from raw production traces.

**Fact (research frontier):** Agent-as-a-Router/ACRouter (June 2026) is exactly the "learn from live execution without upfront benchmarks" proposal: a Contextâ†’Actionâ†’Feedback loop where a Verifier grades outcomes during deployment and a Memory module accumulates "execution-grounded experience," evaluated by cumulative regret on streaming tasks (CodeRouterBench, ~10K tasks, 8 frontier models) ([arXiv 2606.22902](https://arxiv.org/html/2606.22902)) **[HARD]**. **The key insight for coding: coding agents emit natural labels for free â€” tests pass/fail, patch applies, task resolves, PR merges â€” which is exactly the "execution-verified" supervision TwinRouterBench uses (downgrade-and-cascade tiers on SWE-bench, verified by official task resolution)** ([arXiv 2605.18859](https://arxiv.org/html/2605.18859)) **[HARD]**. Inference: routing-from-traces is feasible specifically in domains with executable ground truth, and coding is the best such domain â€” but nobody ships this commercially yet.

### Q4. Academic research on routing for agents

Timeline: **RouterBench** (Martian, 2024) â€” first standardized single-turn router benchmark, now considered restricted to early-generation models. **RouteLLM** (ICLR 2025) â€” preference-data routing, 85%/45%/35% cost cuts at 95% GPT-4 quality. **LLMRouterBench** (Jan 2026) â€” 400K+ instances, 21 datasets, 33 models incl. GPT-5/Claude 4/Gemini 2.5 Pro, 10 baselines, unified framework; its related-work table also catalogs EmbedLLM, RouterEval, FusionFactory, RouterArena ([arXiv 2601.07206](https://arxiv.org/abs/2601.07206v1)) **[HARD]**. **TwinRouterBench** (May 2026) â€” first *step-level* agentic routing benchmark: 970 execution-verified router-visible prefixes from SWE-bench/BFCL/mtRAG/QMSum, plus a live dynamic track running routers inside full SWE-bench Verified agent executions, scored on official task resolution + realized API spend ([arXiv 2605.18859](https://arxiv.org/html/2605.18859)) **[HARD]**. **Agent-as-a-Router / CodeRouterBench** (June 2026) â€” routing as online learning; adding task-dimension performance statistics to a vanilla LLM router yields 15.3% relative gain, showing the bottleneck is information, not classifier capacity ([arXiv 2606.22902](https://arxiv.org/html/2606.22902)) **[HARD]**. The field's direction is unambiguous: from single-shot classification toward execution-grounded, step-level, streaming routing â€” with coding agents as the primary testbed.

### Q5. Do coding agents actually flow through OpenRouter/LiteLLM? What share of tokens is coding?

**Hard data â€” this is now the best-documented part of the market.** OpenRouter's own **State of AI study** (100T-token empirical analysis): **programming grew from ~11% of usage in early 2025 to >50% by mid-2026**, and **agentic workflows generate over half of platform output tokens**; Anthropic holds >60% of the programming category; Chinese open-weight models took ~61% of total token consumption by Feb 2026, disproportionately on coding ([openrouter.ai/state-of-ai](https://openrouter.ai/state-of-ai), [Resultsense summary](https://www.resultsense.com/insights/2026-01-27-openrouter-state-of-ai-100-trillion-token-study/), [Wing VC](https://www.wing.vc/content/chinas-open-weight-takeover), [EULab](https://eulab.ai/articles/2026-02-26/chinese-ai-models-dominate-openrouter-market-share)) **[HARD]**. App-level: the public apps board (captured daily by third parties) shows **top coding tools routing >1.4T tokens/day through OpenRouter â€” OpenClaw ~822B/day, Kilo Code ~302B, Claude Code ~166B (only its OpenRouter slice), Cline ~97B, Hermes Agent ~64B, Roo Code ~21B**; Cline alone has routed 1.01T tokens cumulatively and ranks #2 in IDE extensions ([digitalapplied](https://www.digitalapplied.com/blog/ai-coding-ide-wars-openclaw-kilo-code-claude-code-cline-2026), [agentsdirectory](https://agentsdirectory.dev/rankings/agents), [OpenRouter Cline page](https://openrouter.ai/apps?url=https%3A%2F%2Fcline.bot%2F)) **[HARD, with the caveat that daily figures fluctuate and vendor-native agents like Claude Code/Codex are undercounted because most of their traffic goes direct to Anthropic/OpenAI]**. LiteLLM's coding-agent flow is not publicly quantified, but the documented Claude Code integration patterns and community proxies (e.g., [claude-code-proxy](https://github.com/exospherehost/claude-code-proxy) routing across Vertex/Bedrock/Anthropic to burn cloud credits) show it's an established pattern **[MED]**. **Answer: yes â€” coding is now the majority workload of the largest public gateway, ~5x share growth in 18 months.**

## 4. Is Generic Routing Enough for Coding Workflows?

**Facts first.** (1) Coding is now the majority workload on the largest gateway (>50% of OpenRouter usage, from 11% in early 2025). (2) All shipped commercial routing is per-prompt classification with session stickiness; the one coding-specific commercial router (Not Diamond Code) is in early access. (3) The 2026 research consensus is that one-shot routing is structurally wrong for agents: routers never see intermediate agent state, never verify downstream task success, and suffer "information deficit" that execution feedback demonstrably closes (+15.3% relative gain from task-dimension statistics alone). (4) The engineering-intelligence vendors have shown that token-level cost and PR-level outcome data live in different systems, and that raw throughput metrics mislead (+98% PRs, +91% review time, flat DORA).

**Inference.** Generic routing is *not* enough for coding workflows, for three structural reasons. First, the unit of value is wrong: chat routing optimizes per-response quality, but a coding agent's economic unit is the *task/trajectory* (a resolved issue, a merged PR), where a cheap model at step 12 can silently poison step 40 â€” precisely what TwinRouterBench's downgrade-and-cascade protocol measures and what no commercial router optimizes. Second, the feedback loop is wrong: generic routers train on static preference/eval datasets, while coding produces continuous, objective, free labels (compile, test pass, patch apply, CI green, PR merge, revert) that current routers don't ingest. Third, the deployment surface is wrong: coding agents (Claude Code, Codex, Cline) control their own step orchestration; a gateway sees opaque per-call traffic mid-trajectory and even deliberately pins models for cache economics â€” re-routing mid-session fights both caching and agent-harness assumptions.

**What data would coding-aware routing need?** Synthesizing the benchmarks' supervision schemes and the gateway/EI gap: (a) **router-visible trajectory prefixes** â€” not just the current prompt but agent step index, tool-call history, and remaining-budget context (TwinRouterBench's core construct); (b) **execution-verified outcome labels** joined back to every model call â€” test results, patch application, task resolution, and downstream PR events (merge, modification, revert) â€” i.e., a join between gateway request logs and git/CI systems that today *no vendor performs* (Q7/Q8 finding); (c) **per-step counterfactual or cascade data** â€” which cheaper model would have sufficed at this step, obtainable via sampled downgrade experiments in live traffic or offline replay (the downgrade-and-cascade / cumulative-regret methods); (d) **cost accounting at the trajectory level** â€” realized API spend per resolved task, not per request, so the objective becomes "cost per verified task success" â€” the infrastructure twin of the "cost per merged PR" metric the engineering-intelligence vendors compute manually.
